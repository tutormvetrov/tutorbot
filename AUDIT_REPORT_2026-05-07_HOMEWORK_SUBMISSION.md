# Аудит: учёт «отправленной учеником домашки»

Дата: 2026-05-07.
Ветка: `claude/flamboyant-burnell-8875ce`.
Метод: статический разбор кода (без запуска тестов на этом проходе — менялась только аналитика).

## Кратко: как сейчас устроен учёт

«Отправка ДЗ учеником» в текущей логике сводится к нажатию одной кнопки
«✅ Отметить как выполненное» в карточке ДЗ. Файл/фото/работа в бот не
загружаются — система верит ученику на слово.

Поток:

1. Учитель создаёт ДЗ → строка в `homework` (`status='active'`).
2. Ученик в карточке нажимает `hw_done:{id}` → `mark_homework_done`
   делает `UPDATE homework SET status='done' WHERE id=$1 AND student_id=$2 AND status='active'`.
3. Хэндлер посылает `ADMIN_ID` информационное сообщение
   «✅ ДЗ выполнено!» (без интерактивных кнопок).
4. В пульсе/тачах/нюджах статус 'done' учитывается косвенно через
   `WHERE status='active'` фильтры.

Соответствующие файлы:

- `utils/db_api/homework.py:266` — `mark_homework_done`.
- `handlers/users/callbacks.py:1304` — обработчик `hw_done:{id}`.
- `keyboards/inline.py:151` — клавиатура карточки ученика
  (кнопка «выполнено» только при `status='active'`).
- `utils/db_api/schema.py:138` — таблица `homework` (нет столбца
  `completed_at` / `submitted_at`).

## Что работает корректно

- Идемпотентность отметки: `mark_homework_done` фильтрует по
  `status='active'`, так что повторное нажатие не «откатывает»
  запись. Хэндлер ещё и предварительно проверяет статус и сообщает
  «уже отмечено как выполненное».
- Доступ строго по владельцу: и в SQL, и в хэндлере проверяется
  `student_id`. Учесть чужое ДЗ нельзя.
- Список выполненных доступен и ученику (`hw:done`), и родителю
  (`parent:child:{link_id}:homework:done`) через
  `get_parent_child_homework(..., status='done')`.
- Фильтр «ожидает отправки» в очереди доставки корректно отсекает
  done-ДЗ — `get_due_homework_deliveries` имеет `WHERE h.status='active'`.

## Найденные проблемы

### 1. Нет таймстемпа фактической сдачи (`completed_at`)

В `homework` есть только `created_at`. Когда ученик нажал «выполнено» —
неизвестно. Последствия:

- Невозможно отличить «сдал в срок» от «нажал кнопку через 2 недели после дедлайна».
- В пульсе `last_hw_created_at` отражает только активность учителя,
  не ученика. Учитель не видит метрики «когда последний раз ученик
  что-либо сдал».
- Любой будущий отчёт по дисциплине ученика придётся строить
  ретроактивно по `homework.status='done'` без даты.

### 2. Уведомление учителю — без действий

При сдаче админу уходит только текстовое сообщение
(`handlers/users/callbacks.py:1331-1340`). Нет ни «открыть карточку»,
ни «ответить ученику», ни «вернуть в активные». Сравните с другими
уведомлениями (новое ДЗ, оплата, пропуск) — у тех есть
`make_teacher_reply_keyboard(...)`. Кольцо обратной связи разомкнуто:
ученик отметил → учитель прочитал → дальше тупик.

### 3. Невозможно «отменить» сдачу

Если ученик нажал «выполнено» по ошибке — ни у ученика, ни у учителя
нет UI вернуть статус в `active`. В клавиатуре `done`-карточки только
кнопка «открыть файл» и «написать по ДЗ». Учитель тоже не может
откатить статус из админки (`make_homework_manage_actions_keyboard`
вряд ли знает про done — в `_render_admin_homework_manage` нет фильтра
`status`, но `get_all_active_homework` показывает только active, так
что done-ДЗ из списка просто исчезает).

### 4. Нет детекта «просрочено»

`homework_reminder_job` шлёт только одно напоминание за 20-28 часов
до дедлайна (`utils/db_api/homework.py:274`). Если дедлайн прошёл, а
ученик не нажал «выполнено» — статус остаётся `active`, никаких
сигналов ни ученику, ни учителю. Карточка ученика просто
накапливает просроченные «активные» задания.

Следствие: `has_active_hw=true` в `get_touch_candidates` склеивает
«ДЗ выдано, ещё актуально» и «ДЗ выдано три недели назад, человек
забил». Логика тачей принимает просроченное ДЗ за «ученик в работе».

### 5. `reminder_sent` не сбрасывается при `update_homework`

`update_homework` (`utils/db_api/homework.py:51`) не трогает
`reminder_sent`. Если учитель сдвигает дедлайн со «вчера» на «через
неделю», предзавтрашнее напоминание ученику уже не сработает —
флаг остался `true`. Аналогично — если деадлайн меняли, и
изначальный был дальше, чем «через 28 часов», то напоминание
прозвучит, флаг встанет, и при последующем переносе вперёд
повторного напоминания не будет.

### 6. `homework_check_reminder_sent` не сбрасывается при удалении ДЗ

`mark_homework_check_reminder_sent` ставится в `homework_gap_check_job`
после первого нюджа учителю «между уроками не задано ДЗ». Но если
учитель потом создаёт ДЗ и сразу же удаляет его (например, ошибся
учеником) — нюдж снова не сработает: `lessons.homework_check_reminder_sent`
уже `true`. Ловушка нагляднее с появлением `delete_homework`
(`utils/db_api/homework.py:259`), который физически удаляет строку.

### 7. `handle_hw_auto_resolve` определён, но нигде не вызывается

`utils/nudge_engine.py:121` — функция, которая закрывает все открытые
`homework_nudges` ученика, как только учитель создаёт новое ДЗ.
`grep -rn "handle_hw_auto_resolve" handlers/ utils/` показывает
**только определение**. Ни `add_homework`, ни админский хэндлер не
дёргают её.

Последствие: после того, как нюдж дошёл до stage 3, и учитель потом
всё-таки задал ДЗ, нюдж так и останется `resolved_at IS NULL`. Он
больше не попадёт в `get_lessons_needing_nudge` (там `NOT EXISTS`
по новому ДЗ), но:
- `count_open_nudges(student_id)` будет завышен;
- `get_all_pulse_data().open_nudge_count` тоже завышен —
  это подсвечивает «красным» ученика, у которого ДЗ уже выдано;
- по `homework_nudges` нельзя построить корректный исторический
  отчёт (часть «висит» нерешённой навсегда).

Это самая явная незакольцованность в системе.

### 8. Сдача ученика не считается «закрытием» нюджей и тачей

`mark_homework_done` обновляет только `homework.status`. Не
закрывает `homework_nudges` (резонно — нюджи про учителя, не
ученика), но и не пишет ничего в `student_touches` и не сбрасывает
никакой «тёплый» статус. Если для пульса учитывать факт сдачи
ученика — придётся отдельную метрику добавлять.

### 9. Список «выполненные» растёт навсегда

`get_student_homework(student_id, 'done')` возвращает все done-ДЗ
без лимитов и пагинации. У активного ученика после года это пара
сотен записей в одном сообщении, отрисовывается через
`make_homework_list_keyboard` без `limit`. Не критично, но в перспективе
сломает Telegram-лимит на длину сообщения / число кнопок.

### 10. Никакого артефакта сдачи

Кнопочный «done» — это самооценка. Нет загрузки фото/файла в качестве
доказательства. Это, возможно, осознанный выбор продукта (бот не
претендует на проверку), но тогда стоит явно зафиксировать в
спецификации, чтобы не появлялись частичные попытки сделать «настоящую»
сдачу. На текущий момент в `docs/superpowers/specs` беглого упоминания
такого решения я не увидел.

## Оценка «закольцованности»

| Цепочка | Замкнута? |
|---|---|
| Учитель → ученик: создание/обновление ДЗ → доставка → видно в карточке | Да, проработано в апреле (см. `AUDIT_REPORT_2026-04-10_HOMEWORK_DELIVERY.md`). |
| Ученик → учитель: «отметил выполненным» → уведомление + действия | Нет. Сообщение есть, действий нет (см. п.2). |
| Ученик: создал → напомнили → отметил → сразу видно, как сдал в срок | Нет. Нет `completed_at`, нет «просрочено» (п.1, п.4). |
| Учитель: открытые нюджи → реакция → корректное закрытие | Нет. `handle_hw_auto_resolve` мёртвый (п.7). |
| Правка ДЗ → ре-арм напоминания | Нет (п.5). |
| Удаление ДЗ → ре-арм проверки «нет ДЗ между уроками» | Нет (п.6). |

Половина внешнего контура замкнута, обратное направление и
жизненный цикл «после сдачи / после правки» — нет.

## Рекомендации (в порядке приоритета)

1. **Добавить `homework.completed_at` и заполнять его в
   `mark_homework_done`.** Без этого вся аналитика будущих фич по
   ученической дисциплине будет невозможна.
2. **Дёргать `handle_hw_auto_resolve` из `add_homework`** (или из
   админского хэндлера сразу после `db.add_homework`). Это устранит
   накопление «зомби-нюджей» и приведёт `open_nudge_count` в
   соответствие реальности.
3. **Добавить кнопки в админское уведомление о сдаче ДЗ**: «Открыть
   карточку», «Написать ученику», «Вернуть в активные» (с
   отдельной операцией `unmark_homework_done`).
4. **Сбрасывать `reminder_sent` при `update_homework`**, если меняется
   `deadline`. Можно одним SQL: `SET reminder_sent=false` в
   `update_homework`, либо точнее — только при изменении даты.
5. **Сбрасывать `lessons.homework_check_reminder_sent`, когда ДЗ
   удалили** (`delete_homework`) — если для этой связки урок→ДЗ
   ничего больше не висит.
6. **Завести отдельный статус «overdue»** или хотя бы фоновую
   задачу, которая раз в день считает «активные ДЗ с прошедшим
   дедлайном» и шлёт мягкий пинг ученику + сводку учителю. Сейчас
   просрочка — слепая зона.
7. **Зафиксировать в спецификации**, что «сдача» = нажатие кнопки
   и не предполагает артефакт. Если когда-нибудь захотим артефакт —
   ввести отдельный поток `homework_submissions(homework_id,
   submitted_at, attachment_file_id, note)`, не подменяя текущий
   статус.
8. **Пагинация done-списка** ученика после ~20 элементов.

## Вывод

Учёт «уже отправленной» работает на минимально достаточном уровне
для статуса `active/done` и не врёт в простых сценариях. Но как
система он не ощущается завершённым: нет `completed_at`, нет
обратной петли с учителем, нет реакции на просрочку и правку, и
есть один прямой баг — `handle_hw_auto_resolve` определён, но
никогда не вызывается, из-за чего метрики пульса систематически
завышаются. Перечисленные в рекомендациях правки можно делать
независимыми мелкими PR; самые срочные — пп. 1, 2, 4.
